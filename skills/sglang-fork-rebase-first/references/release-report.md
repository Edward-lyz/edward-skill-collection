# 提测发版报告（KU 发版格式）

发版报告不是自由格式。第一版没按知识库的发版文档排版，被打回重写；以下骨架取自团队过往的发版文档（DSv4.1
v15.9.3.1 那篇），章节号、表头和顺序都不要改。

## 章节骨架

```
# 1.引擎新版本整体信息
## 1.1.变更综述            两列表：项目背景 / 提测的内容 / 提测引擎版本 / 提测 icafe 卡片 /
                           变更所在代码分支 / 预期变更范围 / 对产品自身运维的影响 / 版本发布流水线
## 1.2.变更feature列表      先一段「主要变更内容」编号列表，再三列表：feature / 类型 / 负责人
# 性能测试                  没做就写「未做」和原因
# 功能和长稳报告            开头一段说明：测试对象、对比列是哪个版本、各项测试所用镜像
### 1.2.1.功能回归         流水线链接 + think/nothink × 本版本/上一发版 的 failed/passed/skipped
### 1.2.2.精度回归         OpenCompass 与 EvalScope FC：分组 / 预期 / 本版本 / 上一发版，附构建链接
### 1.2.3.长稳测试         压测流水线链接与参数；没做写「未执行（原因）」
### 1.2.4 兼容性测试       新旧混部是否可行
## 1.3.依赖提前升级模块清单
## 1.4.升级依赖顺序和回滚依赖顺序
# 2.QA发版测试环境构建     2.1 依赖模块环境升级清单；2.2 其他 TODO（提测环境、model_id、就绪检查结果）
# 3.上线
## 3.1.上线时间             表头保留，空着
## 3.2.上线内容            加粗写镜像地址
### 3.2.1.部署配置         image / resources 等，按 E、P、D 节点分行，修改前 → 修改后
### 3.2.2.启动参数         逐参数一行：参数 / 节点 / 修改类型（修改、删除、新增）/ 修改前 / 修改后
```

3.2.1 与 3.2.2 的「修改前」取上一发版的 YAML（仓库里是 `release_epd/base_<版本>/`），「修改后」取本次部署的
YAML，用程序做逐行差分，不凭记忆写（这一轮用证据目录里的一次性脚本 `ku/gen_ku_tables.py` 生成，E/P/D 三角色
各出一组行；它没有进仓库）。

## 写法规则

- 流水线结果原样写入，包括失败、平台判「不达标」和跳过的项；不为了好看改判定标准。构建号和链接逐项给全。
- 没执行的写「未执行」加原因；修复后没重跑的写「推断，未实测」。每项结果注明所用镜像 tag。
- 对比列永远是上一发版，同一流水线、同一入口（都经 AS）。基线与被测不是同一代时（FC 的基线是 V3.2）写明。
- 版本号由发版同学分配；分配前写「待发版同学分配，当前只有 CI 镜像 tag」，不要自拟。
- 精简版：去掉过程叙述和缺陷修复经过，保留 1.1、1.2 表、功能和长稳报告各表、3.2 两张表。完整版保留在本地证据
  目录，精简版发 KU。
- 变更 feature 表只列实际 pick 的卡；默认范围外的（A1/A3/A5/B）若被用户扩大进来，类型列写清。

## 发 KU

用本 skill 的 `bin/ku`，命令见 references/ku-publish.md。先建在个人库，标题带「（精简版，草稿）」；移到发版目录、删除旧草稿、用 `cover` 覆盖全文，
这三件都要用户明确同意。局部 `replace_range` 的选区匹配不稳，更新内容就重新 `create-doc`。
DSv4.1 的发版目录是 repo `VPxwT-t6VJ` 下的 doc `Vg4Gv2VXezICHO`，格式样本是 v15.9.3.1 那篇 `vptXRO7IkodS_6`。
