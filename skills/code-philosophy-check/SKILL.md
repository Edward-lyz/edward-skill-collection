# Code Philosophy Check — 代码哲学自查

检查本次会话修改/新增的代码，逐一对照代码哲学原则。

## 执行步骤

1. 用 Glob/Grep 列出本次通过 Write/Edit 修改的代码文件（.py .cu .cuh .cpp .c .h .hpp .js .ts .rs .go .sh 等）
2. 逐文件 Read，逐条对照下方原则检查
3. **只输出发现的违反项**（格式：`` `文件名:行号` — 违反原则 → 修改建议 ``）
4. 无问题：不输出任何内容，直接结束

---

## 代码哲学原则

### KISS（保持简单）
有无为假想需求预留的扩展点、过度封装、提前抽象？三行能搞定的有没有写成函数？函数能搞定的有没有写成类？

### 命名至上
变量名/函数名/类名是否清晰表达含义和意图？有无 `data`、`tmp`、`handle`、`result` 等含糊词？能否不追溯上下文就理解名字代表什么？

### 谨慎注释
注释是否在重复代码「做什么」（而非解释「为什么」）？能通过重命名解决的有没有去写注释？

### 高性能
热路径上有无不必要的内存分配、重复计算、无效 IO？关键路径有无垃圾实现？有无性能隐患未标注？**禁止**回退思想——遇到难点必须克服，不用低效折中。

### 禁止状态机
有无引入状态机这种过度工程化的结构？应用简洁的编码思路替代。

### 自解释性
没有上下文的人能在 10 秒内理解每段代码的意图吗？代码是否不言自明，不过度依赖注释？

### 单一职责
描述函数时有无用到「和」字？（暗示需要拆分）一个函数是否只做一件事？

### 防御式编程
公共接口是否在入口处校验输入？内部代码有无不必要的防御？assert 是否用于拦截不可能发生的状态？边界是否恰好在公共接口而非内部扩散？

### 变量最小作用域
变量声明是否靠近使用处？有无复用变量存储不同含义的值？作用域是否从最小开始？

### 克制的 DRY
仅重复两次的逻辑有没有被提前抽象？（明确重复三次以上才该提取；过早抽象比重复更有害）

### 并行开发
有无本可并行派发给 sub agent 却串行执行的独立任务？
